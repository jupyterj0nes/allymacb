# Changelog

## v0.3.0 — 2026-11-09

### Forensically strict: the run neither shows in the timeline nor writes on the evidence

- **Extracted archives** are timelined from the times the archive gives its entries, never from the copy the extraction writes. Before, every folder the extraction made for a file came out with the time of the analysis, and every file carried `rule m_before_b (medium)`, because its modification time (from the archive) was compared with the copy's creation time (now): a false finding made by the tool. Now an entry gives one `m...` row at its archive time, files and directories alike; a folder the archive does not hold has no row; a gzip member with no time (`MTIME` 0) has none instead of the extraction time; and no rule sees a time of the copy.
- **Folders of the host** (`-d` walks, `-f` of an unrecognised file) are timelined from their metadata as found: every path is stat'ed before the run opens it, a directory before it is listed, and the walk works from that picture. Before, the access time of a file the run had read to recognise it, and of a directory it had listed, came out as the time of the analysis.
- **Nothing is written on the evidence.** Every file and directory of the evidence is opened with its access time frozen (`src/evidence.rs`): on Windows `SetFileTime` with a last access time of `0xFFFFFFFF_FFFFFFFF` on the handle, which writes nothing and keeps the file system from updating it; on Linux `O_NOATIME`. That covers the parsers, archives, images, the segments of an E01 (now found and opened here, the `ewf` crate reading from them) and the directory listings. Before, running the tool on a folder wrote new access times on what it read, which the next tool, or the next run, then saw. Where the freeze cannot be had (a read-only medium, a file of another owner on Linux, an Ex01, which the `ewf` crate opens itself), the run says how many paths were read the ordinary way.
- Checked: every time of the 394 files and folders of the corpus is unchanged after running all 53 cases (the binary before: 68 changed); three runs in a row on the same folder give the same CSV; on the whole corpus the only rows that differ from the binary before are `fs` rows, the ones above. `cargo test` checks it on folders, archives, a gzip member, an image, a bodyfile and an archive read by their parsers, and fails when the freeze, the listing freeze or the archive-only times are taken out.

### Every processor, the same bytes

allymacb now uses every logical processor the system reports; `--threads N` sets how many, and `--threads 1` runs the code exactly as before. The output does not depend on it: the CSV, stderr, the exit code, `--hunt-out` and the resident dump are byte for byte the same on any number of threads.

- Inputs are read several at a time: the files given with `-f`, the folders given with `-d`, and every `$MFT`, journal, bodyfile, image and archive found in a folder. Their rows are put together in the order the inputs were given; their messages are kept and printed input by input in that order, as if one followed the other. Progress bars are hidden while several inputs are read: they would draw over each other.
- The hunt numbers volumes and records as the parsers meet them. Each input numbers its own from zero, and they are moved, in input order, to the numbers a sequential run gives.
- `--carve`: the free-space search for log lines and `utmp` records, most of the carving time, runs on every thread, a batch of blocks at a time. The scan for `FILE` and `INDX` records, the order hits are taken in, the first copy of a line kept, every count, stay as they were.
- The timeline is sorted on every thread (a stable sort on the same keys) and its rows are formatted on every thread and written in order.
- With `-r` the inputs are read one after another: which source gets the plain name of a path shared by two must not depend on which thread is faster.
- Before, archives found in a folder were already read in parallel, and their messages came out in whatever order the threads finished. They now come out in order too.
- Checked with `scripts/same_output.py`, which records what one binary writes for every sample and checks that another writes the same bytes on every thread count. On 53 cases (every public and lab sample, a 437,000-record `$MFT`, eight hosts in one folder, archives, partial and failed runs, the resident dump), against the binary before this change: 265 of 265 runs identical on 1, 2, 3, 8 and 12 threads, and 140 of 140 in ten more runs of the heaviest cases on 12. `cargo test` runs every fixture, alone and together, on 1, 2, 3 and 8 threads, and the free-space search with log lines planted across every boundary of small blocks. Each of these tests was seen to fail with a bug planted on purpose (results put together in thread order, messages in the wrong order, the hunt's numbers not moved, hits taken out of order, temporary names from a shared counter).
- Measured on 12 logical processors, median of three runs: a folder of eight hosts 38.0 s to 21.0 s; `--carve` on images 41 to 50 % less time (E01 3.3 s to 1.7 s); one 437,000-record `$MFT` 17.9 s to 13.4 s. Peak memory on the eight hosts 2.13 GB to 2.28 GB.
- Temporary files are named after the place of their input in the run, not by a counter the threads share, so the paths printed on stderr are the same on any number of threads.

### The resident dump never overwrites

- Nothing is dumped unless `-r <DIR>` names the folder, and that folder must be new or empty: the files in it are those of the run, and nothing already there is touched.
- A file is created only if no file has its name, in one step (`create_new`). Two records with the same path, from one `$MFT` or from two hosts in the same run, used to leave only the last one when they also shared the record number (`name.rec<N>` was overwritten); with archives read in parallel two threads could both find a name free. Now the second is `name.rec<N>`, the next `name.rec<N>_2`, and so on.
- `--resident-report` is written once, with the totals of every source; it used to be rewritten by each `$MFT`, leaving the last one's counts. It needs `--resident` and refuses a file that exists.

### XFS and LVM

RHEL, Rocky, Alma and Oracle Linux install XFS, and put the root in LVM; Ubuntu Server puts its ext4 in LVM too. Until now allymacb saw neither.

- **XFS** (`source` = `xfs`), read with the [rust-fs-xfs](https://github.com/antimatter-studios/rust-fs-xfs) driver faramir uses, as a partition, a logical volume or a bare image. The tree is walked from the superblock's root inode, and every inode of every allocation group is read from the inode B+trees, 64 at a time: four times with nanoseconds, `crtime` on v5 filesystems. A freed inode keeps its creation time and the time of its last change, usually the deletion: it is a row with `deleted` = `unallocated`. Its name comes back from the free runs of a directory stored in blocks, where removal leaves the low half of the inode number and the name (`(dir slack)`); a short-form directory keeps nothing. In-use inodes no path reaches are `/[UNKNOWN]/inode_N`. With `--carve`, the free space of a plain XFS partition comes from its free-space B+trees.
- **LVM2** physical volumes are recognised by their label, in a partition or as a bare image, and every linear logical volume is read as the ext4 (journal included) or XFS it holds, through the `lvm2` crate. `volume` and `evidence` name it `p1:vg/lv`. A volume that is striped, mirrored, thin or partly on another disk is reported as unreadable and the timeline is partial (exit 3), not silently skipped.
- The volume's birth, which starts the installation window, is the root directory's creation on every Unix filesystem: inode 2 on ext2/3/4, the superblock's root inode on XFS, the `/` line of a bodyfile.
- Error codes `E4101` (XFS superblock), `E4102` (XFS root directory unreadable) and `E4201` (LVM metadata).
- Checked on faramir's fixtures, built on a real host: GPT with XFS, MBR with LVM and XFS, MBR with LVM and ext4. Every file of the populated root, `crtime` and nanoseconds, the freed inodes with the deletion time matching their directory's change, and the three removed files named by the ext4 journal through the logical volume. `scripts/xfs_lab.sh` builds an XFS volume with a large directory, deletions and timestomps, and a `stat` truth file, for the directory-slack names.

### The volume speaks before the rules

A rule judges one record; on a clean Windows Server 2016 the rules alone made 8,169 records `significant` and 17,078 `candidate` (85,327 rows), because two things in a volume's own history make them fire by the thousand. allymacb now reads that history off the `$MFT` (or the Unix root) first (`src/context.rs`).

- **The installation window is `baseline`.** The volume's birth is the creation time of its first record; the window runs from that hour through every following hour that still changed one record in a thousand of the volume (on the reference, four hours in which 98 % of the records changed, image extraction and servicing setting times by hand: 16,615 of its 16,964 `b_after_c`, 918 of its 2,061 timestomp pairs). A record changed inside the window, with no time later than its end, was installed with the volume: `baseline`, its time rules keep their clause and add nothing (the convention: a rule on an entry something vouches for adds nothing; a name rule and `backdated` still count). A `$UsnJrnl` given with the `$MFT` of the same volume takes the same window.
- **The hour is judged against the hours of clean machines.** Outside the window, the records with the same rules changed in the same hour are judged by the share of the hour's changed records that carry each pattern, against the same share in the hours of clean machines (`src/hours.rs`, written by `scripts/measure_hours.py` from the reference hosts: 14 `$MFT` hours, 12 journal hours, 11 Unix hours; the timestomp pair measured as one pattern). The p is empirical with the add-one correction, as in masstin's graph-hunt. Above `--alpha`, a clean machine does that: `habitual`, no points, the clause gives the numbers (`1139 of the 3319 records changed in 2026-11-03T10 carry si_before_fn+si_subsec_zero and 1 of 14 clean hours reach that share (what a clean machine does)`). At or below, one operation: the first record keeps the state and the points, the others are `habitual` and point at it. A pattern no clean hour has (`future`, `pre_1980`, the names, `backdated`) is never explained and never folded: every record keeps its state (`… carry future and no clean hour has that pattern`). The first boot of a virtual machine and the hourly touch of `UsrClass.dat` are clean hours, so a case's hour that looks like them is judged like them. A rate test against the per-record average (Poisson) was tried first and rejected: a clean machine is not average hour by hour.
- **Measured: clean hosts give nothing, planted stomps are found or honestly missed.** Three clean hosts, rules alone: 0 `significant`, 0 `candidate` on PTR-SRV01 (the reference), on PTR-DC01 (same image, never measured) and on LEO-LNX01. Twenty timestomps written into PTR-SRV01's `$MFT`: rules alone find the five pushed into the future with no false positive (precision 1.00, recall 0.25); the five `SetFileTime` stomps carry the signature but are `habitual`, a share the reference's own first boot reaches; the ten consistent copies show no static pattern. The hunt with the cutoff after the first boot finds 15 of 20. `scripts/check_precision.py` scores a timeline and a hunt CSV against the truth file. `double_ext` no longer fires on PowerShell's `__PSScriptPolicyTest_<random>.<random>.ps1`.
- `stats::poisson_tail`, the tail of a Poisson count summed in log space, is the burst test.

### Rule rarity measured on a modern Windows and a whole Linux root

- **The NTFS reference is the `$MFT` of a clean Windows Server 2016 lab host** read from the live volume (431,153 records; the NIST Hacking Case `$MFT`, Windows XP, 12,183 records, was the previous one), with its `$UsnJrnl:$J` (273,208 records) for the USN rule; **the Unix reference is the whole ext4 root of a clean Ubuntu 22.04 lab host** (77,881 inodes, a bodyfile with birth times; a 256 MB image of 861 inodes before). What changed: `si_before_fn` alone fires on a quarter of a modern Windows (the install keeps the image's `$SI` times) and is noise there, 6 points, no state; the pair with `si_subsec_zero` stays the timestomp signature at 23; `b_after_c` 14; `usn_basic_info` is measured, 16; a pattern that never fired is worth 56 on NTFS, 54 on the journal and 49 on Unix (41 and 29 before); `m_after_c` is measured on Unix (never fired, 49). `backdated` and `m_before_b` on NTFS stay unmeasured.

### The timeline lines up with masstin's, column for column

The CSV has masstin's 19 columns: 14 that describe the event, each in the position of the masstin column closest in meaning, then the five-column analysis tail the four tools share (masstin, caarea, faramir and allymacb), so their timelines read side by side and a case tool maps the tail once.

- **19 columns.** `time_created,host,action,type,source,uid,gid,volume,size,mode,deleted,meta,file_name,evidence` and `hunt,hunt_score,hunt_why,verdict,notes`. `host` takes the place of the `[host]` prefix `file_name` used to carry; `action` says what a USN record did (`created`, `deleted`, `renamed`, `modified`, `metadata`); `volume` is `C:` for a loose `$MFT` or `$J` and `p1`, `p2`... for the partitions of an image; `deleted` says how a file is known to be gone (`unallocated`, `dtime`, `usn`) instead of a ` (deleted)` tag in its name; `evidence` names the input from the outside in, as masstin's `log_filename` does (`disk.E01:p2:$MFT`, `kape.zip:C/$MFT`). The `flags` column is gone: the rules speak in the tail.
- **Statistical hunt for manipulated timestamps** (`--investigation-from`, `--alpha`, `--hunt-out`). Records active from the cutoff on are tested against the earlier records of the same volume (conformal p-values, Benjamini-Hochberg); every row gets the verdict on its record. `hunt_score` is masstin's `-10 · log10(q)`, 0 to 100, and stderr prints the highest score each volume can reach. `--hunt-out` writes the findings table in the 19 columns of masstin's, with allymacb's names. On the NIST Hacking Case `$MFT` with 20 timestomps written into it: 14 significant, no false positive.

### The tail speaks the shared convention

The tail follows masstin's `docs/csv-format.md`, section "The same tail in caarea, faramir and allymacb".

- **`hunt` has masstin's six words only:** `significant`, `candidate`, `habitual`, `not_evaluated`, `baseline` or nothing. A high rule (what the timeline called `ALERT`) gives `significant`, a medium one (`WARN`) `candidate`, and when a test and a rule both speak the stronger state wins. `suspicious` and `review` are no longer written: `suspicious` is the analyst's word, in `verdict`.
- **`hunt_why` names the source.** Each rule's clause begins with its id and level, `rule si_before_fn (high): $SI creation before the $FILE_NAME creation`, strongest first, separated by `; `, before the test's words. It replaces the `ALERT: a+b` / `WARN: a` head. Filtering `hunt_why` on `rule ` keeps what the rules said.
- **`hunt_score` is rarity for rules too.** A row with rules alone used to have an empty score. A rule now adds its rarity measured on a clean volume, `10 · log10(records / records that fire)` on the 12,183 file records of the NIST Hacking Case `$MFT`: `si_before_fn` 16, `si_subsec_zero` 17, the two together 17 (measured as a pair, not summed), `b_after_c` 17, and 41 for `future`, `pre_1980` and the name rules, which fired on none. The Unix rules, `usn_basic_info`, `backdated` and every rule on a non-NTFS row are not measured yet: they add 0 and their clause ends with `rarity not measured`. Test and rules add, capped at 100.
- The `rules` column of `--hunt-out` gives the ids with their level, `future (high)+b_after_c (medium)`. stderr says `high-level` / `medium-level` and where each lands in the tail.
- **The 14 event columns are unchanged, byte for byte**, against the build before this change: the NIST `$MFT` with and without the hunt (33,809 rows), a VHD with two partitions carved, a raw ext4 image, a UAC collection and a `$J`. Only the tail differs.
